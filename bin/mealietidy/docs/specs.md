# mealietidy — Specification for a Python CLI Tool

**Status:** Initial specification for a tool whose source code is kept in this Git repository. **Canonical data language:** Italian. **Scope:** The food catalog of one self-hosted Mealie instance, accessed through its REST API. **Selected command:** `mealietidy`.

## 1. Goal and context

The Mealie instance imports recipes from URLs, but some catalog foods have untranslated names or inconsistent synonyms. This increases the manual work needed to match recipe ingredients to existing foods. The tool must export the catalog, identify foods needing Italian names, plurals, or multilingual aliases, identify possible duplicates, support suggestions from future providers or manual review, and apply **only approved changes** in a traceable, repeatable way.

Fixing Cloudflare/FlareSolverr and scraping URLs are outside the scope. The tool does not change recipes to work around the parser. It may use sample ingredients to measure whether a tidied catalog improves matching.

The project and executable are named `mealietidy`. The entry point in its own `pyproject.toml` must use that name. Install the tool locally with `uv`, following this repository's tool installation convention. Git versions the source code only. Catalog exports, plans, reviews, reports, and journals are local runtime files stored in user-chosen directories outside the source repository; they do not need version control.

## 2. Binding principles

1. **Discover before implementing writes.** Do not hard-code endpoints, methods, schemas, permissions, or merge behavior inferred from examples for other versions. Start with the local Mealie v3.28.0 test instance, then repeat discovery for the actual instance when its URL is provided. Record each instance's version, OpenAPI document, and capabilities; stop if required capabilities are missing.
2. **No implicit writes.** `export` (including its discovery step), `analyze`, `edit`, and `apply --dry-run` are read-only with respect to Mealie. Only `apply` without `--dry-run` writes, and only for explicitly approved rows. A separate one-time development test may write to the disposable local Compose instance to verify API discovery; it is never part of `export`.
3. **Identify foods by ID.** Names can change; the Mealie ID is the reference. Never delete or merge automatically based only on textual similarity.
4. **Preserve data.** When an update requires a complete document, fetch it again immediately before writing and preserve every field outside the proposal, according to the instance's schema. If the schema forbids unknown properties, block the change and require a verified adapter instead of sending them.
5. **Keep writes auditable.** Retain the snapshot needed to check preconditions and a local operation journal needed to understand partial application. These files are operational evidence, not a version history. Restoring the installation remains a separate procedure tested by the operator.
6. **Fail closed.** For an unknown version or API, ambiguous response, conflict, validation error, or unexpected difference, block the affected write and report why.
7. **Run without version control.** Install the CLI locally with `uv` on a computer with a supported Python version. Once installed, it must run without Git or a source checkout. Use file contents, IDs, hashes, and local manifests to validate and resume work; never rely on commits, branches, or repository history for runtime state.

## 3. API discovery and compatibility

The [official Mealie API documentation](https://mealie.io/documentation/getting-started/api-usage/) says each installation exposes interactive documentation at `/docs`, tokens are created from the user profile, and many lists are paginated. This guides discovery; it does **not** define food endpoints or guarantee that every version handles aliases, plurals, or merges the same way.

For implementation and testing, create a local Mealie instance from `compose.test.yaml` pinned to v3.28.0. Seed each fresh test database with Mealie's built-in `en-US` Foods seeder before integration tests; do not replace its default catalog with hand-made fixtures. Its food catalog and database are disposable: do not mount named, bind, or anonymous data volumes for Mealie or any database service. Keep the Compose project isolated so teardown removes only this test environment. Verify that a fresh start after teardown contains none of the foods created by tests, then seed it again for the next test run. A separate `compose.yaml` provides an automatically seeded, disposable instance for manual development. The actual Mealie URL will be provided after implementation is complete; do not make it a prerequisite for local development.

Before implementing writes, in order:

1. Start the local v3.28.0 Compose instance and record its local base URL, database configuration, and access method. When the actual instance becomes available, obtain its base URL, version, access method (including any reverse proxy), and database type separately. Do not put private URLs, tokens, or data in the repository.
2. Inspect `/docs` on the **instance being tested** and fetch the OpenAPI document it actually uses. If the document cannot be accessed, stop with a clear error; do not accept a manually supplied copy. Store its hash and the instance's stated version in the export manifest.
3. Identify and document food list and detail reads, pagination, name/plural/alias fields, any usage count, update operations and their semantics (partial update or replacement), any merge operation, error codes, authentication, and limits. Do not infer that a merge is safe from its operation name alone.
4. Perform a one-time development integration test, separate from the final `export` command, on the local Compose instance: create a dummy food, update every relevant field, then reread it to verify that its ID, aliases, extra properties, relationships, and any references remain intact. This checks that the discovered v3.28.0 API's update behavior matches the tool's assumptions. If it fails, writing with `apply` stays disabled. When the actual instance becomes available, repeat read-only discovery as the first step of `export`; if its API differs, keep writing disabled until the differences are verified in a safe test environment. Never use `export` to create or update a food.
5. Package the verified compatibility records with the installed CLI and document them in the source repository. Each record contains the tested Mealie version, OpenAPI hash, verified operations, request/response shapes, test result, and known limits. Store the current instance's discovered version, OpenAPI hash, operation shapes, and matching compatibility status under the selected plan directory. An unrecognized version or hash remains unverified, even if its operations look similar; `export` may still read the catalog, but `apply` cannot write until that combination is verified in a safe test environment and included in a later installed release. The installed CLI must not need access to the source repository.

The public API reference can help orientation, but the tested instance is the source of truth for its own behavior. A successful local v3.28.0 test does not establish compatibility with the later actual instance. The [official discussion about aliases](https://github.com/mealie-recipes/mealie/discussions/4219) notes that their effect on the parser can depend on the version. Verify behavior with real examples; do not promise that every alias improves every search or import.

## 4. Proposed CLI contract

```text
mealietidy export --base-url URL [--token TOKEN] [--plan DIR]
mealietidy analyze [--plan DIR] [--provider none|PROVIDER] [--refine] [--provider-arg-NAME=VALUE ...]
mealietidy edit [--plan DIR]
mealietidy apply --base-url URL [--token TOKEN] [--plan DIR] [--dry-run]
mealietidy config
```

This is the desired interface, **not** a claim that these commands already exist. All values needed for a run must be passable by flags: `--token` supplies the Mealie token. Provider-specific values use the repeatable `--provider-arg-<arg_name>=<arg_value>` form; the selected provider defines required and accepted names and rejects missing, unknown, or duplicate arguments. `--provider` accepts `none`, `codex`, and `gtranslate`; `none` accepts no provider arguments, `codex` accepts `model`, `reasoning-effort`, and `timeout`, and `gtranslate` requires `google-api-key` and optionally accepts `timeout`. Reject unknown providers clearly. Future provider credentials may also be supplied through provider arguments. Invoking `apply` without `--dry-run` authorizes the approved writes after all checks; no additional confirmation prompt or flag is required. Provide `--help` and `--version` on every command. `--base-url` identifies one instance; reject URLs with embedded credentials. Make timeouts configurable with cautious defaults. Commands return a nonzero exit code on errors, conflicts, or incomplete plans.

At startup, read `mealietidy.yaml` in the current working directory when present. Its flat keys match option names with underscores (`base_url`, `token`, `plan`, `timeout`, `provider`, `dry_run`, `refine`); `provider_args` is a mapping of argument names to strings. Underscores in YAML provider argument names map to hyphens in CLI names; reject duplicate names after normalization. Every operational option can also come from `MEALIETIDY_<OPTION>` environment variables, with `MEALIETIDY_PROVIDER_ARG_<NAME>` for provider arguments; underscores in `<NAME>` map to hyphens in the argument name. Continue to accept `MEALIE_TOKEN` as a fallback alias for `MEALIETIDY_TOKEN`. Resolve each option in this order: explicit CLI flag, environment variable, YAML, built-in default. Boolean environment values accept `true`/`false`, `yes`/`no`, `on`/`off`, and `1`/`0`. `--help` and `--version` remain CLI actions, not settings. `mealietidy config` creates a private `mealietidy.yaml` with the current defaults if missing; otherwise it adds missing defaults while preserving existing values and comments. In the generated YAML, `provider` and `provider_args` are the final settings; the active default is `provider: none` with `provider_args: {}`. Separate commented examples for other providers place the matching `provider` value before each `provider_args` block. Existing generated examples may be updated to this layout without changing active values. If no defaults or examples are missing, it leaves the file unchanged. It reports the resulting status and path. The operator edits the file separately with a tool of their choice. Reject malformed YAML without changing it. Keep any token in a private local file outside the source repository.

Every command uses `./mealietidy-plan` relative to its current working directory unless `--plan DIR` selects another root. `export` creates the root and stores discovery details and the catalog snapshot there; `analyze` adds `plan.json` and `review.csv`. The operator can edit `review.csv` directly or use `edit`, which serves a local browser page on `127.0.0.1` with compact review controls and two food columns on wide screens, falling back to one column on narrower screens. Foods with no pending operations start collapsed and show only the name and chips until expanded. Each food can be expanded or collapsed, its heading stays visible beneath the review controls while scrolling through that food, and it shows chips with approved, rejected, and pending operation counts; an Unsaved chip indicates edits that differ from the saved CSV. Search, Previous, and Next retain edits from the current page in the running editor session. One **Save** button validates and writes all accumulated edits across visited pages to `review.csv` in one operation, showing success or failure without reloading the page when JavaScript is enabled. Saved work persists across browser and CLI sessions; unsaved edits require the current editor process and can be lost if it stops or the operator leaves the page without using its navigation controls. `edit` can load recipe-use counts for duplicate candidates through its same-origin local server route when given optional `--base-url` and `--token` settings; the token is never sent to browser JavaScript. Without credentials, review remains available and counts are unavailable. It validates edited rows before replacing the CSV, refuses a stale page when the CSV has changed, and leaves the existing file intact on validation failure. `apply` validates the CSV before contacting Mealie, then stores reports and its journal under the same root. Use subdirectories as needed, with paths relative to the plan root so it remains portable. Run from a local data directory outside the source repository, or pass `--plan`. Never silently overwrite existing export or plan artifacts.

`export` performs read-only API discovery first and only then fetches the catalog. `apply --dry-run` validates the manually edited CSV and previews the current plan without writing to Mealie; a prior dry run is optional. `apply` without `--dry-run` performs the same validation and preflight checks itself before any write. Paths are ordinary filesystem paths and must work outside any Git checkout.

For a second provider pass, run `analyze --provider NAME --refine`. The provider receives only foods with eligible pending operations and sees their existing proposals. A returned suggestion replaces its matching pending operation; omitted suggestions keep their prior values. Approved, rejected, and manually edited pending rows, including notes, are preserved. Without `--refine`, analyzing an existing plan requires interactive `[y/N]` confirmation and requests fresh suggestions for eligible pending operations from the original catalog. Both modes validate the existing plan and review first, then update their matching fields together; they do not contact Mealie. `refine` is also available as a YAML boolean and `MEALIETIDY_REFINE` environment variable. The plan's root `provider` and `provider_info` identify the latest pass.

## 5. Export and analysis

### Export

First discover the instance's version, fetch its OpenAPI document, and identify authentication needs, pagination, and food operations without writing to Mealie. If the OpenAPI document is inaccessible or the required food read and pagination capabilities are missing or ambiguous, stop with a clear error before exporting. Record missing or unverified write capabilities as an `apply` blocker; they do not prevent a read-only export. Then read **every** page of foods, not just the first batch. Check totals, duplicate IDs, and count stability. If data changes during export, report an inconsistent snapshot and retry or stop. Save the discovery record, original JSON for each food, and a manifest with the UTC date, normalized base URL, Mealie version, OpenAPI hash, record count, totals, and checksums under the selected plan directory. Preserve raw data without destructive normalization. A readable CSV can accompany the JSON; JSON is the source for preconditions and recovery. No export step creates a Git commit or requires a repository.

Do not confuse a catalog export with a full backup. The [official Mealie backup guide](https://mealie.io/documentation/getting-started/usage/backups-and-restoring/) describes installation backup and restoration. The operator is responsible for deciding whether to back up the instance before `apply`; the CLI does not check for a backup or block writes when one is absent. Restoration may be destructive; test it in a test environment first.

### Deterministic analysis

- Normalize **only for comparison**: Unicode NFC, repeated whitespace, and casefolding. Keep the original for writes. Do not blindly strip accents, apostrophes, or punctuation.
- Find empty fields, names that may not be Italian, missing plurals, repeated aliases within a food, and name/alias collisions across foods.
- Identify possible duplicates using separate signals: normalized equality, spelling variants, known translations, and lexical similarity. Similarity does not establish that two foods are identical.
- Classify suggestions as `safe_candidate`, `needs_review`, or `blocked`, with reasons and provenance. A high score alone never approves a suggestion.
- Culinary equivalents are not always interchangeable: form, species, processing, allergens, dried/fresh state, whole/ground state, units, and brand may require separate foods.

### Italian names, plurals, and aliases

The canonical name should be natural, specific Italian without losing useful distinctions. The plural must be grammatically correct for the full name. If it is invariant or uncertain, suggest an appropriate value or leave it empty according to verified Mealie behavior. Avoid naive rules such as replacing the final letter. Keep the original name as an alias **only if** that creates no ambiguity. Aliases may include Italian, English, and other languages found in the user's recipes. Each alias must refer to the same food, not a culinary substitute. Deduplicate by normalized comparison while preserving the chosen spelling. Do not add an alias that matches another food's name or alias without explicit review. Record language and rationale in the local plan; do not assume Mealie stores language metadata for aliases.

## 6. Interchangeable suggestion providers

AI is optional and only **suggests** translations, plurals, aliases, and possible duplicate pairs. Use a small strategy interface, `suggest(foods, context) -> (suggestions, failed_batches)`, so analysis can select a provider from a registry without depending on its implementation. Each provider validates its own `--provider-arg-<arg_name>=<arg_value>` inputs and handles its own batching, progress, and failures. The deterministic `none` strategy flags possible untranslated names and missing plurals for manual review but does not generate Italian names or suggest translations. Rows requiring an operator-supplied name or plural remain pending with an empty `proposed_value` until reviewed. The optional `codex` adapter invokes the locally installed Codex CLI through `codex exec`, using an existing ChatGPT login rather than an OpenAI API key. It suggests names, plurals, and aliases in batches; deterministic analysis continues to flag possible duplicates. Other providers may be added later by implementing the same interface and registering a factory; do not add their dependencies or configuration to the core before they exist.

Selecting `codex` through a flag, environment variable, or local YAML explicitly opts into sending the minimum food names, existing plurals, and alias names to OpenAI's cloud service. Document the recipient, account-plan limits, and applicable retention controls before use. Invoke Codex outside the repository in an empty temporary directory, with read-only sandboxing and no API key inherited from the environment. Show progress as foods processed out of the total before and after each batch, including failed batches. Keep all suggestions pending; failures, invalid output, repeated actions, and collisions must never become approved changes. Cache validated batch responses by input, prompt version, and selected model in the private plan directory. Default to the fast `gpt-6-luna` model when `model` is omitted; the operator may select another model with the Codex provider's `model` argument. The optional `reasoning-effort` argument overrides Codex's built-in effort for that model and must be included in provider metadata and the suggestion cache key when set; unrecognized levels are rejected before analysis, while model-specific support is checked by Codex.

The optional `gtranslate` provider uses Google Cloud Translation Basic v2 with the standard NMT model. It sends only food names to Google, detects the source language, and proposes Italian canonical names for manual review with high uncertainty; it does not infer plurals, aliases, or merges. It requires an API key from a billing-enabled Google Cloud project, supplied as the `google-api-key` provider argument; `timeout` is optional. The key must not be saved in the plan, cache, or logs. Cache validated responses in the private plan directory. Limit new requests to 16,000 input characters per analysis and 5,000 characters per request; skipped batches remain pending with provider-error findings. The first 500,000 characters per month are covered by Google’s shared Cloud Translation NMT credit, but a local per-run cap cannot account for other uses or repeated runs. Recommend a dedicated project with its Cloud Translation general-model daily character quota set to at most 16,000, which caps 31 days at 496,000 characters. Google processes Basic requests on a global endpoint; its data-usage FAQ says submitted text is held briefly in memory and is not used to improve its models. [Pricing](https://cloud.google.com/products/translate/pricing), [quotas](https://docs.cloud.google.com/translate/quotas), [data usage](https://docs.cloud.google.com/translate/data-usage).

The output contract includes source ID, proposed field, value, language, short rationale, uncertainty, and related candidate IDs. Validate schema, lengths, empty values, and ID references before creating a plan. Treat catalog text and model output as **untrusted data**; do not execute embedded instructions. Never send tokens, private URLs, backups, complete recipes, or personal data to the model. Send only names and the minimum needed context, with explicit consent for remote providers. Cache by input hash and prompt/model version for reproducibility and cost control. Errors or invalid output result in `needs_review`, never a write.

## 7. CSV and JSON review plan

The plan records a `schema_version` for format validation; it does not maintain revisions or history of data files. Start the schema at `1.0.0` and follow SemVer: compatible additions use minor or patch updates, while breaking changes require a major update. The tool reads older plans within the implemented schema's major version and warns whenever a plan's `schema_version` is older. Reject unsupported major versions and schema versions newer than the reader supports with a clear error. The tool version is provenance only and must not gate plan reading. Reading an older compatible plan must not rewrite it. A later phase must add an explicit migration that creates a new plan at the current schema version and requires review again; no migration is required in the initial release.

`plan.json` retains the full structure and checksums; `review.csv` stores human decisions, with the local HTML editor as the primary interface. Direct CSV editing remains supported. Keep the plan, its reviewable files, and the snapshot and discovery evidence they require together in the plan directory so it remains usable when copied to another computer or location. Use relative references within that directory rather than paths tied to the original computer. Use UTF-8 and fixed headers. One row represents **one operation on one food**. A merge uses a separate row and always requires manual review. Minimum fields:

| Field                              | Meaning                                                    |
| ---------------------------------- | ---------------------------------------------------------- |
| `operation_id`                     | Stable identifier generated by the plan.                   |
| `food_id`                          | Mealie ID of the target record.                            |
| `action`                           | `rename`, `set_plural`, `add_alias`, or `merge_candidate`. |
| `current_value` / `proposed_value` | Before and after; for aliases, the value to add; conflict resolution uses `merge:<retained_food_id>` or `delete:<food_id>`. In a conflict page, a colliding rename or alias can be converted using `resolve:merge:<other_food_id>:<retained_food_id>` or `resolve:delete:<other_food_id>:<deleted_food_id>`. |
| `language`                         | Proposed language, where applicable.                       |
| `duplicate_target_id`              | ID of the other food in a duplicate candidate; `proposed_value` selects which participant to retain. |
| `evidence` / `reason`              | Readable source and rationale.                             |
| `risk`                             | `low`, `medium`, or `high`.                                |
| `decision`                         | `pending`, `approve`, or `reject`; initially `pending`.    |
| `reviewer_note`                    | User's free-form note.                                     |

In JSON, also include `snapshot_hash`, `record_hash`, `openapi_hash`, timestamps, tool version, the provider name in `provider` and non-sensitive provider metadata such as the optional model in `provider_info`, normalization settings, and fields needed to reconstruct the suggestion. The baseline `plan.json` and its source checksums are immutable. In `review.csv`, only `proposed_value`, `decision`, and `reviewer_note` may change; every other field, the header, and the set of rows must match the baseline plan exactly. Reject added, removed, or duplicate rows. A pending or rejected row may have an empty `proposed_value` when analysis cannot produce a reliable suggestion; an approved row must have a valid nonempty value. Give rows with no generated value a `high` baseline risk, so an operator-supplied value can be reviewed without changing the immutable risk field. Validate edited values and decisions against the original snapshot on every `apply` invocation, with or without `--dry-run`. Reclassify an edited `proposed_value` and report its effective risk; if the value is invalid, creates a conflict, or exceeds the baseline risk, reject it and require a regenerated plan and new review. Record a checksum of the reviewed CSV in each preflight report, but never trust an earlier report in place of current validation. Do not treat an arbitrary CSV as a write command. Provide summaries by risk, action, and decision.

The baseline remains fixed for review and `apply` between analysis passes. An explicit second analysis may replace the baseline fields of eligible untouched pending rows in both files, as described above; it must preserve every approved, rejected, or manually edited row.

Illustrative example only:

```csv
operation_id,food_id,action,current_value,proposed_value,language,duplicate_target_id,evidence,reason,risk,decision,reviewer_note
op-001,ID-123,add_alias,,tomatoes,en,,manual,"Same food; English form",low,approve,
```

## 8. Apply and preview

### Shared preflight

Every `apply` invocation starts by validating `review.csv` against the immutable `plan.json` and the applied operations in `journal.jsonl` locally, before contacting Mealie. Then run the same read-only preflight: confirm the current instance and OpenAPI hash match the export, require a packaged compatibility record verified for that version and hash, and fetch every affected food. For a food without verified operations, require its current record to match `record_hash` and the snapshot. For a food with verified operations, require its current record to match the journal's latest verified after-hash. Skip verified operations and group only newly approved operations for one update to that food. A group with an uncertain write outcome must be reread and reconciled with the journal before any retry. Any other difference, including a changed ID or unrelated field, blocks that food and requires a new export and manual review. Show the per-food diff, preserved fields, skipped operations, and blocked foods. Validate schema and preconditions; do not check write permissions in preflight. Do not send POST/PUT/PATCH/DELETE requests or make implicit AI calls during preflight. Save machine-readable and human-readable reports with checksums for the plan, validated review CSV, and current discovery under the plan directory. An approved `merge_candidate` is an explicit resolution: its `proposed_value` must be `merge:<food_id>` where the ID is one of the two candidate foods and identifies the retained food. Validate all approved merges before any write. A blocked food does not prevent independent approved foods from being written; report the partial result and exit nonzero. A plan-wide validation failure blocks all writes.

With `--dry-run`, return after this report without writing to Mealie. The preview does not establish write permission. Without `--dry-run`, continue to the write gates below using the freshly checked state. A previous preview report is never required or used to authorize writes.

### Apply writes

Required prerequisites: a token, compatible discovery, and approved rows in `review.csv`. The `apply` command itself authorizes writing the approved changes; do not prompt for additional confirmation. Show the number of approved changes in the summary, but impose no maximum change count. Backup creation and restore testing are the operator's responsibility; `apply` does not require backup evidence.

Group newly approved, nonconflicting operations for each `food_id` before writing, then process one pending food at a time. Immediately reread the food, check the group's preconditions against its verified state, and apply only the new changes in one API update. Append the attempt, outcome, food ID, operation IDs and values, and before/after hashes to a journal. Verified operation values and decisions are immutable; later review cycles may change other rows without invalidating verified operations. The editor hides applied rows by default and offers a read-only Show applied view based on the local journal, which does not attest to the current Mealie state. Existing journals without operation values can be upgraded when the unchanged review is opened in the editor; unresolved legacy outcomes must first be reconciled with `apply`. If the review was already changed, recreate the plan. Do not log tokens or sensitive data. If Mealie rejects a write for insufficient permissions, log a clear error identifying the affected food and operation IDs, record the failed attempt, exit with a nonzero status, and make no further writes. After each successful write, reread the food and verify that only the approved fields changed and all others were preserved; record its verified after-hash in the journal. Stop on other errors as well; do not continue after uncertain results. Automatically retry only requests known not to have run, or after a reread proves the state. Never blindly replay writes. Use rate limiting and backoff for temporary responses without hiding permanent errors.

**Idempotency:** Repeating the same plan must make zero changes when the desired state is already present. `add_alias` uses a duplicate-free union; `rename` and `set_plural` check both current and desired values. If a change was applied but the client did not receive confirmation, reread before any retry. An unrelated concurrent change blocks the write until the plan is regenerated. There is no global transaction guarantee: the journal identifies partial application and supports controlled resumption.

### Conservative deduplication

Duplicate candidates always require an explicit review decision. On a supported instance, approve a merge by selecting which candidate to retain. `apply` requires an exact packaged version and OpenAPI compatibility record for the merge endpoint and both recipe and shopping-list count endpoints. It checks counts before and after, preserves the retained food's fields, adds the source name and aliases as aliases, invokes Mealie's merge endpoint, then verifies the source is gone and the reference counts moved to the retained food. It blocks before writing if either food changed since export, source aliases collide with another food, or catalog substitution links are defined on the source or point to it from another food. It checks these links again immediately before the merge write. The error identifies the source food and tells the operator to resolve the links in Mealie, then export and analyze a new plan. The journal records the merge attempt and verified result so interrupted applies can be reconciled safely.

An operator may also explicitly choose one candidate for deletion. `apply` allows this only on a packaged verified version and only when current recipe, shopping-list, incoming substitution, and outgoing substitution reference counts are all zero. It obtains substitution relationships from every page of the current food list, checks all counts again immediately before deletion, then verifies the food is gone and the other candidate is unchanged. It records the delete attempt and verified result in the journal and can reconcile an interrupted response. If a count cannot be read, references exist, or either candidate changed since export, it blocks deletion. Packaged v3.28.0 compatibility was verified on the disposable local instance; the operator has also manually confirmed the expected behavior on the actual v3.28.0 instance. Every run still requires matching version and OpenAPI hash. The operator remains responsible for backups.

## 9. Security and data

- Use HTTPS with TLS verification enabled. Configure a self-hosted certificate through a trusted CA; do not default to `verify=false`.
- Use a token with only the required permissions, preferably dedicated and revocable. Accept secrets through flags as well as environment variables or a secret manager, but never write them to plans, reports, journals, or logs. CLI arguments may be visible in shell history or process listings; document that exposure. Never require users to put tokens or runtime data in the source repository. Do not print sensitive HTTP headers.
- Give local files restrictive permissions; reports may contain private catalog names. Use operator-chosen output directories and document how to keep them outside the source repository and clean them up when no longer needed. No Git-based data history is required.
- Do not add telemetry. Disable remote AI providers by default; document data recipients, costs, and retention before use.
- Restrict the base URL to the expected host; do not follow redirects to another host with Authorization. Guard against requests to arbitrary destinations when reading untrusted configuration.
- Avoid automatic operations on production instances during imports or concurrent edits. Report conflicts instead of overwriting them.

```text
README.md                  # installation, configuration, operating procedure
docs/specs.md              # this document

compose.yaml                # disposable Mealie v3.28.0 instance for manual development

tests/                     # unit tests and anonymized API fixtures

.gitignore                 # local development files, not runtime data storage
```

Separate only necessary boundaries: a Mealie client guided by verified capabilities, pure analysis logic, plan format, write executor, and AI adapters. Do not build a generic framework for other applications. Use the standard library where sufficient; choose HTTP/CLI/test libraries after checking repository constraints. Record a schema version in the plan for validation and resumption; do not implement data revision history. Keep the tool's entry point and dependencies in its own `pyproject.toml` and install it locally through `uv` as described by the root repository guide. Running the installed command must not require the development repository or Git. Store no generated catalog data in the source repository.

## 11. Required tests

Run the complete local suite with `uv run poe test`. The task resets the disposable Compose instance, seeds its built-in `en-US` Foods catalog, discovers `tests/test_*.py`, runs the separate API verification, and tears the instance down. Future automated tests follow the same discovery pattern.

1. Anonymized fixtures for paginated exports: read-only discovery happens first; an inaccessible OpenAPI document stops export clearly, every page is read, IDs are unique, and inconsistent snapshots are detected.
2. Unicode normalization and aliases: accents, apostrophes, whitespace, capitalization, invariant plurals, collisions across records, and culinarily distinct terms. The `none` strategy produces deterministic flags and pending rows without generating Italian names or translation suggestions or launching an AI provider.
3. First step of `apply`: validate allowed edits to `proposed_value`, `decision`, and `reviewer_note`; reject edits to every other field, added or removed rows, nonexistent IDs, invalid decisions, approved rows with empty proposals, edited values that create conflicts or exceed baseline risk, and mismatched hashes before any Mealie call. Allow empty proposals only on pending or rejected rows and operator-supplied values on high-risk pending rows. Read an older same-major schema with a warning; reject unsupported schema majors and newer schemas, and read a plan created by a different tool version when its schema is compatible.
4. `apply --dry-run`: no write calls, correct diff, and concurrent conflicts blocked. `apply` without a previous preview performs the same preflight before writing.
5. Apply against mocks: approved operations only, one update for multiple approved changes to the same food, later approvals on the same or another food without replaying verified operations, applied values and decisions locked, independent foods written despite a blocked food with a nonzero partial-result exit, conflicting rows blocked, an approved `merge_candidate` with verified compatibility, references redirected and counted, aliases preserved, incoming and outgoing source substitutions blocked, deletion blocked by any recipe, shopping-list, or substitution reference, verified zero-reference deletion and resume, unverified compatibility causing zero writes, merge/delete journal reconciliation, unrelated fields preserved, a denied write producing a clear nonzero error and no further writes, second apply with zero writes using its verified journal after-hash, an unrelated concurrent edit blocking a resumed plan, and timeout after a write resolved by rereading.
6. One-time API discovery verification against the local Compose Mealie **v3.28.0** instance, outside the final `export` command: seed the fresh database with Mealie's built-in `en-US` Foods catalog, then create/read/update a dummy food, aliases and plural, compare all fields, and check the parser with real before/after examples. Separately assert that `export` makes no POST/PUT/PATCH/DELETE calls. Test merging only if implemented and verifiable. Confirm no data volumes are mounted and the catalog is empty after teardown and a fresh start, before seeding it again. Run read-only export discovery on the actual instance when its details become available.
7. Security checks: `--token` overrides `MEALIE_TOKEN`; tokens and secret provider arguments never appear in logs or artifacts, cross-host redirects are blocked, TLS is enabled, `none` is selected by default and rejects provider arguments, and unknown providers or provider arguments are rejected. When the local Codex CLI/ChatGPT adapter is added, test that it obeys the same suggestion contract and never writes to Mealie.
8. Portability check: install the package locally with `uv` on a supported Python environment; run export, analyze, and apply against a test instance using `./mealietidy-plan` without a plan path flag, override the shared root with `--plan` on each command, and repeat after copying the plan directory to a different path without Git or a source checkout.

Do not use production data for fixtures or destructive tests. Version-dependent tests must state the Mealie version and OpenAPI hash explicitly.

## 13. Acceptance criteria

- For a known test catalog, `export` fetches the instance's OpenAPI document during read-only discovery, then produces the same set of IDs as the Mealie list and a verifiable manifest. It fails clearly if OpenAPI is inaccessible.
- `export` never sends a write request, including when run against the local test instance; the one-time update verification is a separate development test.
- `analyze` distinguishes possible untranslated names, missing plurals, alias issues, and duplicate candidates; no AI result is applied without review.
- The initial release supports `none` without an AI installation. It does not generate Italian names or translation suggestions; later providers use the same suggestion interface and remain optional.
- Mealie credentials and every provider-specific input can be supplied through flags; each provider accepts only its declared arguments, and sensitive flag values are excluded from saved artifacts and logs.
- The operator can review foods across multiple HTML pages, save all accumulated edits with one button, then resume in a later session. Direct CSV editing remains possible; only `proposed_value`, `decision`, and `reviewer_note` may change. `apply` rejects tampered immutable fields, changed row sets, edited values that create conflicts or exceed baseline risk, and rows tied to another snapshot before any Mealie call. Every invocation validates the current CSV, even if it changed after a preview.
- `export` creates the self-contained `./mealietidy-plan` root by default; `analyze`, `edit`, and `apply` use that root. `--plan` overrides it on every command, and existing artifacts are not overwritten silently.
- An older plan with the same schema major remains readable with a warning regardless of the tool version that created it; incompatible or newer schemas fail clearly without modifying the plan.
- `apply --dry-run` does not change Mealie and previews the operations and blocks. `apply` without a prior preview runs the same preflight and can proceed once all write gates pass.
- Preflight does not check write permission. If Mealie denies a write, `apply` reports the affected food and operations, records the failure, exits nonzero, and stops further writes.
- Without compatible discovery and approvals, `apply` stops before the first write; missing backup evidence does not block it.
- For an approved plan, `apply` preserves unrelated fields and references; a second run makes no writes. An error halfway through leaves a journal useful for resumption.
- Collisions and ambiguous cases are never merged or renamed automatically.
- An approved merge candidate must specify one of its two foods as the retained food. On a packaged compatible instance, merge redirects recipe and shopping-list references, preserves source names/aliases, verifies counts, and can resume after an interrupted response. Unsupported compatibility, changed participants, alias collisions, and catalog substitution links involving the source block the merge before its write.
- Deleting a conflict candidate is allowed only after current recipe, shopping-list, and substitution reference checks all return zero; otherwise `apply` blocks it before the delete request.
- Ingredient matching is compared before and after on sample recipes; regressions are recorded and resolved before broader use.
- The README lets a new contributor install the CLI, export, analyze, review and save progress through `edit`, run `apply --dry-run`, and apply without a prior preview on a test instance without knowing this conversation. It explains that backup decisions belong to the operator.
- An operator can install the CLI locally with `uv` and complete the workflow without Git or a source checkout at runtime. Generated data stays in operator-chosen directories, and plan approval and application use local files and checksums rather than version control.
